## 安装哪些产物

| 项目 | 安装物 | 使用方式 |
| --- | --- | --- |
| SDK | `tansr_sdk-0.1.0-py3-none-any.whl`；`tansr_sdk-0.1.0.tar.gz` | 作为库导入 `tansr_sdk`，不需要 Demo、Node、C++ 或 Rust 运行时 |
| 独立 Demo | `tansr_sdk_demo-0.1.0-py3-none-any.whl`；`tansr_sdk_demo-0.1.0.tar.gz` | 精确依赖 `tansr-sdk==0.1.0`，提供 chat/tools/archive 三个命令和 async_chat 模块示例 |
| 目标依赖 wheelhouse | 对应 Python/OS/架构的已核验依赖文件与哈希清单 | 为隔离安装提供密码库及构建依赖；不能拿另一平台的目录代替 |

`py3-none-any` 描述本 SDK/Demo wheel 的 Python 源码形式，不代表包含的运行能力没有原生依赖：AES-GCM 由 `cryptography` 提供，其 wheel 和旧 Python 的 cffi 等依赖仍有平台约束。包内已带生成操作/schema 与类型标记，应用运行不需要合同生成器、源参考或完整开发仓库。

安装前使用同一份产物清单核对源码版本、SDK/Demo 的版本、每个 wheel/sdist 的实际文件名和 SHA256、依赖锁、目标解释器/OS/架构及安装结果。不要从示例命令推导未知产物哈希，也不要混用前后两轮同版本但字节不同的包。

## 从 PyPI 安装

在适用的虚拟环境中安装；只使用 SDK 时无需安装 Demo：

```text
python -m pip install tansr-sdk==0.1.0
python -m pip install tansr-sdk-demo==0.1.0
python -m pip check
```

## 隔离和离线安装

先选择已核验的完整解释器，不修改系统默认 Python。下面是通用安装步骤，路径均需替换；实际 TLS 适用范围见下一节。

```text
/absolute/python -m venv /absolute/venv
/absolute/venv/bin/python -m pip --isolated --disable-pip-version-check install --no-index --find-links /absolute/wheelhouse /absolute/artifacts/tansr_sdk-0.1.0-py3-none-any.whl
/absolute/venv/bin/python -m pip --isolated check
```

Windows 将 venv 解释器换为 `C:\absolute\venv\Scripts\python.exe`。只使用 SDK 的应用到此即可；需要 Demo 时再以同一解释器安装同批 `tansr_sdk_demo-0.1.0-py3-none-any.whl`，使用相同 `--no-index --find-links`。然后在仓库外的普通目录运行：

```text
python -m pip show tansr-sdk tansr-sdk-demo
python -m tansr_demo.chat --help
python -m tansr_demo.tools --help
python -m tansr_demo.archive --help
```

这里的 `python` 必须仍是该 venv 的完整解释器路径。`--help` 不需要模型、凭据或 Serve；真正运行 Demo 前，还需按指南配置服务地址、当前身份、私有目录及需要的 Source/档案密钥。导入时不得靠开发树 `PYTHONPATH` 或 editable install 掩盖缺包。

wheelhouse 须包含当前目标的完整依赖闭包。离线安装失败时先核对锁和目标标签，不加 `--no-deps` 绕过缺失依赖，不无条件升级旧 Python 的 pip。sdist 消费另需匹配该解释器的 PEP 517 构建依赖；根与 Demo 各有 `pyproject.toml` 分段约束。构建成功、依赖一致、真实 Serve 消费是不同检查，不能互相替代。

## Python 3.7 与 TLS 运行时

运行源码最低 CPython 3.7，排除 3.9.0/3.9.1。这个语法/ABI 兼容声明不使已结束维护的 Python 或 SSL 自动获得安全更新。通过 `python -c "import sys, ssl; print(sys.version); print(ssl.OPENSSL_VERSION)"` 检查实际运行程序，不能只看系统安装列表。

默认 HTTPS 传输要求受支持的 stdlib OpenSSL：1.x 分支至少 1.1.1n，3.x 分支至少 3.0.2；较早版本和未验证 provider 在 DNS/连接前拒绝为 `unsupported_tls_runtime`。这只是 SDK 已知风险的最低防线，不承诺达到门限的旧版本仍有上游维护。`cryptography` 自带的 SSL/密码实现不能替代 stdlib `ssl` 的版本检查。

Windows 官方 CPython 3.7.9 所带 OpenSSL 1.1.1g 保留拒绝，回环 HTTP 成功不是 HTTPS 正向证明。本轮已实际验证下面的 **Windows x64 隔离 legacy 运行时**，继续使用 SDK 原 stdlib 网络栈，没有替换系统 DLL：

| 组件 | 精确来源/构建 | 实际结果 |
| --- | --- | --- |
| CPython | [Anaconda python 3.7.9](https://api.anaconda.org/release/anaconda/python/3.7.9)，win-64 `h60c2a47_0` | `sys.version_info[:3] == (3, 7, 9)` |
| stdlib OpenSSL | [Anaconda openssl 1.1.1w](https://api.anaconda.org/release/anaconda/openssl/1.1.1w)，win-64 `h2bbff1b_0` | `OpenSSL 1.1.1w 11 Sep 2023` |
| 安装器 | [conda-forge micromamba 2.3.3](https://api.anaconda.org/package/conda-forge/micromamba) | 标准 prefix 安装/重定位；仅子进程环境，没有全局 shell hook 或 PATH 修改 |
| 已安装 SDK 网络链 | 原 SDK wheel、空自定义 CA、无业务凭据 | 默认信任 HTTPS 200；原 25 项传输检查通过，包括错误 CA/主机名/过期拒绝、TLS/SSE 取消和期限 |

默认 HTTPS 正向使用 Windows 标准库默认根，未设置 SSL_CERT_FILE/SSL_CERT_DIR，也未传 cafile/capath；不将 conda 的 CA 文件错误宣称为这次请求的显式信任来源。该结果只覆盖本组合，不能外推到其它发行构建、CPU 或所有 3.7 环境。

必须通过标准 activate/run 入口运行，不能裸调用 prefix 的 python.exe。本机实测还发现：某些启动上下文中 `micromamba run` 能让首个解释器载入 SSL，却没有将 `Library/bin` 留在它继承的 PATH 中，导致它创建的子进程或 venv 消费者 `import ssl` 报 DLL load failed。不能只验证首个解释器。

为使子进程和后续孙进程都继承同一套 DLL，采用本轮已验证的进程级启动方式。将下例保存为 `C:\tansr-runtime\run-runtime.py` 并调整三个绝对路径；用已有可用 Python 执行它。它只构造传给子进程的环境，不修改调用者、系统或用户 PATH：

```python
import os
from pathlib import Path
import subprocess
import sys

prefix = Path(r"C:\tansr-runtime\python379")
mamba = Path(r"C:\tools\micromamba.exe")
runtime_root = Path(r"C:\tansr-runtime\mamba-root")
environment = dict(os.environ)
environment.pop("PYTHONHOME", None)
environment.pop("PYTHONPATH", None)
dll_paths = [prefix, prefix / "Library/bin", prefix / "Library/usr/bin",
             prefix / "Library/mingw-w64/bin", prefix / "Scripts"]
environment["PATH"] = os.pathsep.join([str(path) for path in dll_paths] +
                                    [environment.get("PATH", "")])
environment["CONDA_PREFIX"] = str(prefix)
environment["PYTHONNOUSERSITE"] = "1"
command = [str(mamba), "--no-rc", "--no-env", "-r", str(runtime_root),
           "run", "-p", str(prefix), "python"] + sys.argv[1:]
raise SystemExit(subprocess.call(command, env=environment))
```

原 prefix 本身已经是独立环境。若另建 venv，必须在这个入口下执行 `-m venv C:\absolute\venv`；随后使用同样的进程私有环境，在 command 中把最后的 `"python"` 换成该新 venv 的完整 `Scripts\python.exe` 路径。不能复用原 1.1.1g 解释器建立的 venv，也不能只把一个新 python.exe 复制进去。程序若自行传 `env=` 创建子进程，应从当前环境复制并保留这些已激活路径，不能清掉后仍宣称 SSL 环境相同。

这份最小运行时未自动注入 pip。先从同批已校验 wheelhouse 离线引导 pip 24.0，再安装精确运行依赖和 SDK。下面 `$launcherPython` 是用于启动上述脚本的已有解释器；`--no-deps` 仅用于无依赖的 pip 自身引导，不用于跳过 SDK 依赖：

```powershell
$launcherPython = 'C:\absolute\existing-python\python.exe'
$launcher = 'C:\tansr-runtime\run-runtime.py'
& $launcherPython $launcher -I -c 'import sys,ssl;print(sys.version);print(ssl.OPENSSL_VERSION)'
$wheelhouse = 'C:\release\wheelhouse'
$pipWheel = "$wheelhouse\pip-24.0-py3-none-any.whl"
& $launcherPython $launcher -I -c 'import sys,runpy;sys.path.insert(0,sys.argv.pop(1));runpy.run_module(''pip'',run_name=''__main__'')' $pipWheel install --no-index --no-deps $pipWheel
& $launcherPython $launcher -I -m pip install --no-index --find-links $wheelhouse --require-hashes --only-binary=:all: -r 'C:\release\requirements\runtime-py37.lock'
& $launcherPython $launcher -I -m pip install --no-index --find-links $wheelhouse 'C:\release\artifacts\tansr_sdk-0.1.0-py3-none-any.whl'
& $launcherPython $launcher -I -m pip check
```

需要 Demo 时按同样方式安装同版 Demo wheel，再用 `& $launcherPython $launcher -I -m tansr_demo.chat --help`。导入位置应是新 prefix（或新建 venv）的 site-packages；它再启动的 Python 子进程也应读到 OpenSSL 1.1.1w。上述传输检查只证明所列网络范围，不代替 Demo、档案与完整应用验收；其他已验证范围见本页相应章节。

这是可复现兼容环境，不是长期维护承诺。Python 3.7 与 OpenSSL 1.1.1 均已结束维护；[OpenSSL 官方 EOL 公告](https://openssl-library.org/post/2023-09-11-eol-111/) 明确该分支停止公开安全更新。新应用优先选受维护的现代解释器。宿主可另行注入经过独立验证的安全传输并承担其集成验证，Demo 没有替换 transport 的 CLI 开关。不能禁用主机名/证书校验，或误以为添加 CA 文件能够修补不安全的 SSL 运行时。

## macOS Python 3.7 的文件系统能力

SDK 的 POSIX 私有存储通过目录描述符、`O_NOFOLLOW`、相对 `dir_fd` 操作、原子替换和锁维护路径/身份边界。Python 的版本号、CPU 标签以及 TLS 成功均不足以证明这些能力可用；构建时的 macOS deployment target 和特性检测结果也影响运行能力。

本轮已确认 Conda CPython 3.7.12 / x86_64 / macOS 10.9 target 构建虽然支持 TLS，却没有启用所需 `HAVE_OPENAT` 等 `*at` 能力，`os.supports_dir_fd` 为空。SDK 私有目录操作因而拒绝或抛出 `NotImplementedError`；这个环境不能用于本包完整档案/journal/Demo 消费。不能通过去掉 nofollow、把目录相对操作改为裸路径或吞掉异常来宣称支持。

可用以下只读命令检查自己解释器的构建信息；这只是诊断线索，不代替原子写入、权限、链接和真实存储验收：

```python
import os
import platform
import ssl
import sys
import sysconfig

print(sys.version, platform.machine())
print(ssl.OPENSSL_VERSION)
print("deployment_target", sysconfig.get_config_var("MACOSX_DEPLOYMENT_TARGET"))
print("dir_fd", sorted(function.__name__ for function in os.supports_dir_fd))
print("HAVE_OPENAT", sysconfig.get_config_var("HAVE_OPENAT"))
```

### 已通过的本地源码构建

替代路线是官方 CPython 3.7.17 **源码**、本地 x86_64 / deployment target 10.13 隔离编译，并链接已有隔离 OpenSSL 1.1.1w。这不是 python.org 提供的 macOS 3.7.17 二进制安装器，没有改变 SDK 候选或放宽路径检查。本轮已通过实际目录描述符能力、SDK/Demo sdist 的 PEP 517 隔离构建/安装、pip check、三个 CLI 入口、AES-GCM、246 项主测试（0 失败/0 跳过）、默认 HTTPS、sdk1/offload 两族真实异步会话、9 组 Demo 和 tools 实时输出链。会话/Demo 使用实际 Serve 与合成身份/平台/模型，不宣称调用真实付费模型。

| 构建条件 | 本轮采用值 |
| --- | --- |
| 源码 | [Python-3.7.17.tar.xz](https://www.python.org/ftp/python/3.7.17/Python-3.7.17.tar.xz)，SHA256 `7911051ed0422fd54b8f59ffc030f7cf2ae30e0f61bda191800bb040dce4f9d2` |

下面是隔离目录布局的占位示例，应在构建时替换为自己的路径。实际 prefix 改变后须重新构建或正确重定位并验证依赖；这些路径不是固定 SDK 配置：

| 用途 | 示例路径 |
| --- | --- |
| 新 runtime | `$HOME/tansr-runtime/cpython-3.7.17` |
| 新 venv | `$HOME/tansr-runtime/venvs/python3717` |
| 链接的 OpenSSL prefix | `$HOME/tansr-runtime/openssl-1.1.1w` |

创建 venv 使用新 runtime 的 `bin/python3.7 -I -B -m venv <新venv>`；消费使用新 venv 的 `bin/python` 完整路径、清除 PYTHONHOME/PYTHONPATH，从仓外目录安装并运行。新 runtime 的 `_ssl` 依赖构建时指定的 OpenSSL prefix，因此 **必须保留仍被链接的 OpenSSL 目录**，即使同目录中的旧解释器不再使用。仅搬走/复制 venv、覆盖旧 Python 或清理仍被链接的库均不能作为迁移。

该 3.7.17 运行时的默认 CA 来自保留 prefix 下的 `ssl/cert.pem`（解析为 `ssl/cacert.pem`，121 根）；清除 SSL_CERT_FILE/SSL_CERT_DIR、无显式 CA/业务凭据的默认 `HttpTransport()` 请求返回 HTTPS 200。现代 Mac 3.14.8 arm64 格使用 `/private/etc/ssl/cert.pem`（128 根）并同样通过。两者都没有声称自动导入 macOS Keychain；自定义 SSL 构建或部署必须核对实际根来源。

Python 3.7/OpenSSL 1.1.1 的 EOL 边界仍保持，不因本地源码构建消失。目标 10.13 是本构建的 deployment target，不是已经实测所有 macOS 10.13 及以上版本；实际机器/系统与验收范围按回执记录。

## 接线和升级时保留什么

- Serve 负责模型、核心运行、权限/裁决、上下文/记忆和能力协商；终端不持上游模型密钥。SDK 不自动部署 Serve，不附送通用远程 Shell 或设备能力回落。
- 会话族必须保持一致。sdk1 保留原存储路径；offload 依赖授权 Source 和原创建意图，不能在恢复时悄悄改为 sdk1。
- 保存原 session ID、请求 key/body/deadline、执行 journal、档案、key-id 和密钥。失回后查询/恢复原事实，不换 ID、删目录或延长 TTL 重做。
- 更新前停止新操作并等待 handler、磁盘提交和输出收尾真实结束；`close` 返回 False 时依赖尚不能卸载。本地关闭与远端 `Session.close()` 不同。
- 不同语言 SDK 的私有存储格式不直接互换。旧文件、备份和 tombstone 不能通过重命名/合并跳过代际、身份或删除语义。

## 0.1.0 的能力与发行边界

已提供同步/asyncio 高层会话、业务执行器与独立输出确认、加密本地档案及材料供给，以及只消费公开 SDK 的独立 Demo。81 个通用操作并不等于 81 组完整应用体验：本包没有独立 MemoryClient/CacheClient、全自动记忆发布宿主、通用 Shell/PTY、录音/播放或跨设备同步服务。对应低层操作由应用根据 Serve 合同显式接线，不能将本地档案误称完整记忆引擎。

SDK 与 Demo 采用 MIT；各依赖保留各自许可证，使用者应同时遵守。打包工具成功不等于已完成上传。公开源码内容由仓库中的公开合同清单校验，私有服务夹具和开发历史不属于 SDK/Demo 运行产物。正式安装应核对发行版本、产物哈希和目标环境，不能混用同版本的不同候选文件。

## 维护者发布流程

1. 冻结源码，在本地完成合同/生成、格式/类型、测试、构建及独立安装消费门，保留源码与产物哈希。
2. 使用 [export_source.py](https://github.com/tansrai/tansr-python/blob/main/tools/export_source.py) 显式导出逐项批准的 20 份合同资产及公开源码，校验导出清单；不直接推送内部仓库或私有历史。
3. 仅将通过本地检查的公开快照推送到 `tansrai/tansr-python` 的 `main`。不推送开发分支。
4. 等待该提交的 [三系统 CI](https://github.com/tansrai/tansr-python/blob/main/.github/workflows/ci.yml) 成功，记录对应提交 SHA 与 CI run ID。
5. 在同一个 `main` 提交上手动运行 [publish.yml](https://github.com/tansrai/tansr-python/blob/main/.github/workflows/publish.yml)，填写 `ci_run_id` 和 `package`（`sdk`、`demo` 或 `both`）。工作流核对仓库、分支、提交 SHA 和成功状态，下载该次 CI 的原始 `pypi-distributions` artifact，先校验 SDK/Demo 各一份 wheel 和 sdist 共四件产物的身份、MIT 许可及 Python 元数据，再将选中的原文件复制到上传目录，不重新构建。
6. 首次创建两个 PyPI 项目时，同一配置不能同时登记两份 pending publisher。先为 `tansr-sdk` 登记 `tansrai/tansr-python`、`publish.yml`、environment `pypi`，以 `package=sdk` 上传 SDK 两件产物。确认首次使用已将 SDK 的 pending publisher 转为 normal publisher，并核对 SDK 上传结果。
7. 再为 `tansr-sdk-demo` 登记相同仓库、工作流和 environment 的 pending publisher。在同一 `main` 提交上另启动一次发布，仍填写同一个 `ci_run_id`，选择 `package=demo`；新运行通过 OIDC 签发新凭据，处理 Demo 的 pending publisher，并仅上传 Demo 两件原产物。不要复用首轮已签发的 token，也不要重复上传已存在的 SDK 文件。
8. 两个项目均已建立后，后续新版本可选择 `package=both`。发布使用 GitHub `pypi` environment 与 PyPI Trusted Publishing/OIDC；完成后记录实际上传结果、公开文件哈希与安装消费结果，不用构建成功代替发布成功。

## English release-use summary

Version 0.1.0 of the SDK and Demo uses the [MIT license](https://github.com/tansrai/tansr-python/blob/main/LICENSE). Source is distributed through `tansrai/tansr-python`, and the package channel is PyPI. Install `tansr-sdk` alone for embedding; install matching `tansr-sdk-demo==0.1.0` only for the three CLI examples and the async_chat module. Use the artifacts' exact hashes and target-specific dependency wheelhouse, a separate virtual environment and the same full interpreter path for installation and execution. A pure-Python SDK wheel does not remove native cryptography dependencies.

The CPython language/ABI floor is 3.7 (excluding 3.9.0/3.9.1); HTTPS separately requires a supported patched stdlib SSL runtime. Official Windows 3.7.9/OpenSSL 1.1.1g remains rejected. The separate Windows x64 Anaconda Python 3.7.9 `h60c2a47_0` + OpenSSL 1.1.1w `h2bbff1b_0` environment passed installed-SDK default-trust HTTPS and the 25 transport checks. This is a reproducible legacy route, not renewed upstream maintenance.

The explicit eight-package URL/SHA256 list and commands above reproduce that runtime in a private prefix with micromamba 2.3.3. Actual acceptance downloaded/verified those exact files before offline prefix installation. Use the included Python launcher: it copies the environment, removes PYTHONHOME/PYTHONPATH, prepends only the child-process prefix/Library/bin and other standard runtime paths, then invokes `micromamba run`. Some contexts let the first interpreter load SSL without retaining Library/bin for its children; a successful first import alone is insufficient. The launcher does not change global or caller PATH.

If a separate venv is needed, create it through that launcher and retain the same child-only environment when launching its full Scripts/python.exe path. Do not reuse a venv created by the old interpreter or copy replacement DLLs. Bootstrap the verified pip 24.0 wheel, install the target runtime lock offline, then install matching SDK/Demo wheels and run pip check. Check SSL in child interpreters as well. Default HTTPS used Windows stdlib trust with no custom CA or SSL_CERT_FILE/SSL_CERT_DIR overrides. Neither a CA file nor cryptography's separate SSL build bypasses the guard.

Keep Serve identity, family, original deadlines, journals, archive files and keys across recovery. Local close is not remote session close, output confirmation is not the business receipt, and material received is not core-consumed. See the [English guide](https://github.com/tansrai/tansr-python/blob/main/doc/guide.md) for executable SDK-only examples, permissions, tools, async ownership, archives and troubleshooting. Publication results are recorded by the versioned package index and workflow run; the tested combinations on this page do not establish support for unverified environments.

For macOS, directory-descriptor support is a separate requirement. The tested Conda 3.7.12 x86_64/10.9-target build has empty `os.supports_dir_fd` despite working TLS; it cannot satisfy private storage and must not fall back to bare path operations. The alternative local x86_64/10.13-target build from official CPython 3.7.17 source with isolated OpenSSL 1.1.1w passed actual directory capabilities, installed sdist consumption, all 246 main tests with no failures/skips, default HTTPS, both families' real async sessions, nine Demo groups and live tools output. Serve was real, with synthetic identity/platform/model fixtures, not paid-model acceptance. This is a local Rosetta x86_64 build, not an official macOS binary or a native arm64 Python 3.7 claim.

The table above records the exact source hash and configure/build conditions; the directory layout uses placeholders. Retain the OpenSSL prefix linked during the build: `_ssl` depends on those libraries and, in the tested environment, its default CA bundle contained 121 roots. The modern arm64 3.14.8 environment instead used `/private/etc/ssl/cert.pem` (128 roots); neither claims automatic Keychain trust. Create a fresh venv from the new runtime's full `bin/python3.7` path, clear inherited PYTHONHOME/PYTHONPATH, and use the new venv's full executable path. Deployment target 10.13 does not mean every corresponding macOS version was tested, and this legacy build does not restore upstream maintenance.
